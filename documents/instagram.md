# 店の Instagram を、間違えずに集める

図鑑のロースター欄に Instagram を出すために、店のページから
アカウント名を集めている（`scripts/collect_instagram.py` →
`config/instagram.yaml` → 図鑑）。

ここに書くのは、**実データで測って分かったことだけ**。
やってみて駄目だったことも、駄目だった数字ごと残す。

## 1. 埋め込みはできない

記憶で決めず、実際に叩いて確かめた。投稿・プロフィールのどちらも

    HTTP 200 / 63万字 / 最終URL …/accounts/login/?next=…

つまり中身ではなくログイン画面が返る。だから図鑑では
**@名前を出して、Instagram へのリンクを置く**形にしている。
写真を貼ることはできない。仕様が変わることはあるので、
集めるたびに毎回この確認を出している（記憶ではなく応答で判断する）。

## 2. 「よく出てくるもの」は、店のアカウントではない

最初は、店名に似たものが無ければ**いちばん多く出てくるアカウント**を
採っていた。実データで6件、別のアカウントを店のものとして書き込んだ。

| 店 | 拾ったもの | 正体 |
|---|---|---|
| Single O | @process_creative | サイトを作った会社 |
| Padre Coffee | @shopify | 「Powered by Shopify」 |
| 49th Parallel | @49th | 途中で切れた短い断片 |
| Slate Coffee Roasters | @xoilactvnet | 無関係の宣伝。何度も貼られていた |
| Dark Matter Coffee | @ridmanscoffee | "coffee" だけの一致 |
| Comete Coffee Roasters | @interpret_coffee | 同上 |
| LiLo Coffee Roasters | @inthecoffeekyoto | 同上（別の店） |

回数は「店のものらしさ」を測っていない。ページに何度も貼られている
だけのものが勝つ。いまは**綴りと結びつくものだけ**を採る。

    1. 頭が一致する            Padre Coffee    → @padrecoffee
    2. 綴りの揺れ              Coffee Collective → @coffeecollectif
    3. 店名の単語が入っている   Luna            → @enjoylunacoffee
    4. 店のURLの綴り           丸山珈琲(maruyamacoffee.com) → @maruyama_coffee

業種の言葉（coffee / roasters / cafe …）では照らし合わせない。
どの店の名前にも入っているので、そのページに載っている**他店の**
アカウントにも必ず当たる。見分ける力が無い。

規則を厳しくすると取りこぼしも出る。実測では313件中7件が説明できなく
なり、うち3件が上の間違い、4件は正しいもの（略称・日本語の店名）だった。
**正しい4件は表に手で足す**。ファイルの見出しにそう書いてある。

> 間違ったアカウントを出すのは、何も出さないより悪い。
> 別の人の投稿を「この店です」と紹介することになる。
> 取りこぼしは次に集めれば埋まる。

## 3. どこまで取れるか（実測）

443店中 **318店（71.8%）**。残り125店の内訳と、それぞれに何を試したか。

| 理由 | 軒数 | 試したこと | 結果 |
|---|---|---|---|
| リンク無し | 61 | 問い合わせ・about ページも見る | +数軒 |
| 接続失敗 | 48 | www の有無を入れ替えて再試行 | +6軒 |
| HTTP 403 | 13 | Accept を HTML にして名乗り直す | +2軒 |
| 店のものか決められない | 7 | 店のURLの綴りも手がかりにする | 0軒 |
| 404 / 410 / 526 | 6 | — | 店側が閉じている |

同じ条件で繰り返しても増えない。**2回続けて0軒**になった時点で
自動収集は頭打ちと判断した。残りは手で足すか、諦める。

なお 429（レート制限）は、少しずつ回すうちに消えた。
最初の回では120軒中43軒が429だったが、最後の回では0軒。

## 4. 1回の実行に時間の上限を置く

つながらない店に再試行を足したところ、GitHub 側の上限（15分）に届いた。
上限に当たると**その回に取れたぶんまで捨てられる**。
8分で切り上げて、取れたぶんを必ず書き出すようにした。
残りは「時間切れ」として数え、次の回が続きから見る。

## 5. 集めた数と、図鑑に届く数は違う

318件集めたあと、図鑑まで通して数えたら**9件しか出ていなかった**。
「集める」と「届ける」は別の仕事で、集めた数だけを見ていると気づけない。

漏れは3段階で見つかり、そのつど数が変わった。

| 見つけた漏れ | 原因 | 直後の数 |
|---|---|---|
| オーバーレイしか見ていなかった | 巡回の出力は「手書きの表に無い店」しか持たない | 9 → 238 |
| 豆が取れた店しか引けなかった | 図鑑にページはあるが豆が0件の店に付かない | 238 → 308 |
| 名前が違う店を引けなかった | 図鑑「George Howell」/ 表「George Howell Coffee」 | 308 → 309 |

さらに、名前で引くと**別の店に付く**ことが分かった。`norm()` は業種の言葉
（Coffee / Roasters …）を落とすので、

    config/roasters.yaml: Luna（enjoylunacoffee.com）
    図鑑の表:             Luna Coffee（lunacoffeeroasters.com、バンクーバー）

が同じ "luna" に潰れる。そのままだと、バンクーバーの店のページに
別の店のアカウントが出る。**引いたキーのドメインが店のドメインと違うなら使わない**
ことにした。これで De Mello（ドメイン変更）と Fuglen（東京とオスロ）も
落ちるが、間違って出すよりよい。落ちたぶんは書き出しのログに名前が出る。

引き当ての順番は次のとおり。上ほど確か。

    1. ドメインが一致する図鑑の店
    2. 名前が一致し、ドメインが矛盾しない図鑑の店
    3. 巡回で見つけた店（図鑑には手書きの項目が無い）

同じ図鑑の店に2つの店が同じ確からしさで来たら、どちらも付けない。

## 6. 表に残しておいてはいけないもの

店の名前を直したり、店を図鑑から外したりすると、その名前のぶんが
表に残る。誰も使わないまま溜まると「もう持っている」の判断が狂い、
「まだ取れていない店を先に見る」の順番がずれる。
集めるたびに、図鑑に無い名前を外している。

同じことが `state.db` でも起きていた（→ `src/state.py`
`prune_missing_roasters`）。**設定から消しただけでは、データは消えない。**
